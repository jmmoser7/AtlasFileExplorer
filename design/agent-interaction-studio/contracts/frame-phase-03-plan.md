# Frames · Phase 03 Rust Canvas plan

Status: native specimen available for review. See the [Phase 03 run and verification report](../contract-viewer.html?document=contracts/frame-phase-03-receipt.md).

The first runnable slice is the [five-slide JS flow](../?phase=01&tab=frame&sample=1&fixture=presentation-small): select a Frame, open Create Presentation from the toolbar, see the attached palette and continuous highlight, then dismiss it with one blank-canvas click or Esc. The [Frame contract](frame.md) and [100-slide JS flow](../?phase=01&tab=frame&sample=1&fixture=presentation-large) set the reference for the rest. The spec has two distinct orders: a presentation's slide sequence and the physical positions of its Frames on the canvas.

## Implementation sequence

1. **Get the real canvas entry running.** Put the real Frame paint and selection strip on a small Rust canvas with the production transform, hit testing and theme. Extend the Frame branch in Slate's `board_properties.rs` and call the shared `atlas-shell` selection tools, scale, text and dimensions owners. If a Slate app dependency blocks the small harness, extract only the needed production code and make Slate use that same owner. Use the same shared widget for Phase 02 if needed. Start with one blister Frame and one smaller squircle Frame; compare the join, button spacing and chevron to the JS reference before adding the rest.
2. **Give named presentations one document owner.** Extend `slate-doc` with named, ordered references to stable Frame IDs; a Frame may appear in several lists. Keep the legacy `FrameNode.order` sequence as the fallback for boards without named presentations. Define how deleted and hidden Frames resolve, and prove that existing boards open and play in their original order. Use the existing scene journal for membership, reorder and physical sort. Keep the open palette, hover, selection and drag preview in session state. Dismissal or a cancelled drag writes no journal entry.
3. **Wire the five-slide journey.** Extend `board_deck.rs` for the selector and canvas actions: hover a deck name for the map, open from any member Frame, click plus/minus or use the context menu, and drag from blank canvas to add crossed Frames in first-contact order. Delete with a thumbnail selected removes its presentation reference only. Connect compact thumbnails and group drag using Shift/Ctrl. Esc cancels an active gesture first; otherwise Esc or a blank click closes the palette, selector and membership mode. Right-drag pan and wheel zoom keep the native canvas rules.
4. **Exercise the large grid and playback.** Add the [100-slide fixture](../?phase=01&tab=frame&sample=1&fixture=presentation-large) through the same owners. Verify that the whole grid fits at the reference 780 × 720 viewport, rows retain their subtle separators, and a group slides across rows without an insertion divider. Reorder changes only the active deck; **Sort on canvas** moves the Frames with their contents in one undoable operation. In `present.rs`, resolve the selected deck through the same document query and preserve the existing slide navigation, camera flight and Esc return. Include the attached Settings palette in the specimen and exercise video start/loop, web view and interactive 3D policy with deterministic media events.
5. **Attach the runnable Phase 03 specimen and evidence.** Use the real egui output and existing `atlas-shell::frame_raster` for repeatable captures. Compare squircle and blister sizes, idle and hover, the open seam, drag and dismissal against the browser at matched zoom, viewport, DPI and theme. Run the journal tests for cancellation, undo/redo, shared membership and legacy fallback. Attach the runnable artifact and paired captures with source and binary hashes, commands and results, known differences, and cold/warm build timings. Register captures under Frames in Image Studio.

## Build and integration boundary

Use one narrow package or executable and the existing warm target/profile. Check its dependency tree and test configuration before linking; WebView, Rhino, model providers and the whole Slate application should stay outside the specimen's dependency closure. Time the first cold build and one warm edit separately; under 60 seconds for the warm loop is the target to measure.

Full Slate entry, workbook round trips, export ordering and real media hosts still require Phase 04 evidence. Review the existing [Frame acceptance gate](../frame/ACCEPTANCE.md) and native Deck command contract before changing the baseline; preserve the old receipt and document intentional differences. Verify the first native slice before expanding into those integrations.
